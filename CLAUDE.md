## Architecture

This is a Flutter warehouse management app using the **GetX** pattern throughout. The app is organized under `lib/app/` with the following layers:

### Layer Responsibilities

- **`data/models/`** — Plain Dart model classes with `fromJson`/`toJson`.
- **`data/providers/`** — All HTTP calls. Every provider extends `ApiProvider` (which extends `GetConnect`) and inherits the base URL and bearer token injection automatically. Providers call `checkResponse(response)` immediately after every `await get/post/put/delete` call — this throws a descriptive exception for null statusCode or non-2xx responses (preferring the server's `message` field, then appending any `error`/`errors` detail). After `checkResponse`, providers parse and return typed objects. They never catch errors; that is `ApiExecutor`'s job. **Prefer the shared `ApiProvider` helpers** for the three common shapes instead of re-writing `get → checkResponse → parse`: `getList<T>(path, Model.fromJson, {query})` for a `{"data":[...]}` list (null-tolerant), `getMap(path, {query})` for a JSON-object body (pagination envelopes), and `postMap(path, body)` for a POST returning a JSON object. Only single-model getters (`Model.fromJson(response.body['data'])`) and custom parses stay inline.
- **`helpers/api_excecutor.dart`** — `ApiExecutor.run()` is the single wrapper for all controller-level API calls. It checks connectivity, gates on `isLoading` to prevent double-calls, runs the provider task, and shows an `errorAlert` on failure (stripping the `"Exception: "` prefix for clean user-facing messages). Returns `null` on any error so controllers can do a simple `if (data == null) return;`.
- **`services/`** — Long-lived `GetxService` singletons registered in `main()` as `permanent: true`: `AuthService` (token/username/roles stored in `get_storage`), `ApiProvider` (HTTP client), `NetworkService` (connectivity monitoring).
- **`middleware/auth_middleware.dart`** — `AuthMiddleware` is applied to protected routes in `AppPages`; it redirects to `/login` if no token is stored.
- **`modules/`** — Feature modules, each with `bindings/`, `controllers/`, and `views/` subfolders. A binding uses `Get.lazyPut()` to wire providers and controllers together.
- **`routes/`** — `app_routes.dart` defines path constants; `app_pages.dart` maps them to views + bindings + optional middleware.
- **`global/`** — Shared code: `alert.dart` (snackbar helpers), `functions.dart` (formatting/utility), `size_config.dart` (responsive sizing), `variables.dart` (palette constants), `widget/` (reusable widgets), `styles/app_text_style.dart`. Every screen except Home uses the shared chrome: `accent.dart` (`AppAccent` enum — the single color source — plus `navyGradient`, `accentFor(name)`, `readableOnWhite(color)`), `widget/app_header.dart` (`appHeader` navy AppBar, `obxHeader` for Rx subtitles, `headerAction`), `widget/accent_header_card.dart` (`accentHeaderCard` patterned card under the AppBar with `HeaderStat` / `AccentProgress` / `ProgressSegment`, `headerFooterText`; `accentMetricCard` + `HeaderMetric` — the same card as a summary of side-by-side metrics, each with its own gradient icon tile, used by Products), `widget/accent_pill.dart` (`accentPill`, `statusPill` for API colors), `widget/app_buttons.dart` (`navyButton` main action, `accentOutlineButton`, `softIconButton` — square navy-tinted list-header action such as Products' sort/search/filter, found in tests by its tooltip) and `widget/stock_direction_icon.dart` (`stockDirectionIcon` IN/OUT leading), `widget/stock_level_tile.dart` (`stockLevelTile` product-row leading: remaining qty colored by `StockLevel` ok/low/out, low = under 10). The receive/outflow screens share three widget files: `widget/order_menu_widgets.dart` (menu hero/section/tile, `orderMenuInfoCard`, `decorCircle`), `widget/order_list_widgets.dart` (list card, pagination footer, `orderSummaryHeader` + `lineTotals` for Item Summary, `orderRecordHeader` for Receive/Outflow Order detail, item-summary tile, serial line + dialog, and `orderSubmitConfirmDialog` + `SubmitConfirmLine` — the "Continue to Receiving / Outflowing?" confirmation of all four flows: pass only the filled/scanned lines; the list scrolls while Cancel/Continue stay pinned), and `widget/order_fill_widgets.dart` (`orderFillItemHeader`, `orderFillResultsTitle`, scan FAB, navy bottom bar). Master lists (Category/Brand/Unit) use `MasterListView` + `masterListCard(kind: MasterKind.x)`. The scan-flow quantity/serial dialogs (batch qty, other-item qty, receive item qty+expiry, receive number) live in `widget/qty_input_dialogs.dart` — each owns its `TextEditingController` inside a `StatefulWidget` so it is disposed only after the dialog's exit animation. **Never** `dispose()` a controller right after `await Get.dialog(...)`: the future resolves the instant `Get.back()` fires, while the field is still mounted for the close animation, which throws "A TextEditingController was used after being disposed".

### Key Patterns

**Cursor-based pagination** — List controllers hold `cursorNext` (`RxnString`) and `hasMore` (`RxBool`). `loadProducts()` resets the cursor and fetches the first page; `loadMore()` appends the next page. This pattern is used across `product`, `receive_order`, `outflow_order`, and `transaction` modules. The end-of-list line is always `NoMoreDataFooter(size: size)` (`functions_widget.dart`) — it adds bottom room plus the nav-bar inset; don't hand-roll a "No more data" `Text`. **Exception:** the `delivery` module's `GET /delivery` is **not** paginated server-side (returns all rows), so `DeliveryListController` loads everything once and filters/sorts/status-filters **client-side** — no cursor.

**Debounced search** — Search input triggers a 400 ms debounce timer that cancels any pending timer before calling `loadProducts()` again with updated `buildParams()`. Filters (date range, price, qty threshold) are collected in `buildParams()` and sent as query params to the backend.

**Responsive sizing** — `SizeConfig.init(context)` is called once in `MyApp.build`. All sizes throughout the app derive from `SizeConfig.defaultSize` (2.4% of the narrower screen dimension). Pass `size` (the default size value) into widgets rather than hardcoding pixel values.

**Navigation** — All navigation uses `Get.toNamed(AppPages.<constant>)` with named route constants from `app_routes.dart`. Arguments are passed via `Get.toNamed(..., arguments: obj)` and read in the receiving controller via `Get.arguments`.

**Alert helpers** — Use the functions in `global/alert.dart` (`errorAlert`, `successAlertBottom`, `errorAlertBottom`, `warningAlertBottom`, `infoAlertBottom`) for user feedback, not raw `Get.snackbar`. **Snackbar + `Get.back()` pitfall:** in GetX 4.7, `Get.back()` closes an open snackbar *instead of* the route — so a dialog/bottom sheet closed with `Get.back()` right after (or while) a snackbar is showing stays open. **Never call `Get.back()`** — close dialogs, sheets and pages with `closeRoute([result])` from `global/functions.dart`, which pops the root navigator and leaves snackbars alone (covered by `test/helpers/close_route_test.dart`).

**Loading states (Skeletonizer)** — Content/first-load loading uses the **`skeletonizer`** package via shared helpers in `global/widget/skeleton_widgets.dart`, never a plain "Loading…" label. Inside the `Obx`, the loading branch returns a shimmering placeholder that mirrors the real layout: `skeletonOrderList` (lists of `orderListCard`), `skeletonLineList` (`orderSerialLineCard` detail lists), `skeletonSummaryList` (`orderItemSummaryTile` fill/scan lists), or `skeletonGenericList` (product/transaction/master lists). For a screen that shows already-populated/stale data during a refresh, wrap its body in `skeletonize(loading: <flag>, child: <body>)`. Pass the module's accent color (same one its cards use). **Do not** skeletonize button/FAB spinners or infinite-scroll "loading more" footers — those stay as `CircularProgressIndicator`. The legacy `textLoading()` helper is superseded; `textNoData()` is still the empty-state.

**Provider error handling** — Use the shared helpers on `ApiProvider` (`getList`/`getMap`/`postMap`) for the common shapes; only single-model / custom parses stay inline, and those still follow this pattern:
```dart
Future<SomeType> getSomething() async {
  final response = await get('/endpoint');
  checkResponse(response);          // throws for null/non-2xx — do not skip
  return SomeType.fromJson(response.body['data']);
}
```
Never return raw `Response` from a provider. POST methods also call `checkResponse` and return `Map<String, dynamic>` (or a typed model). Do not add try/catch in providers — let exceptions propagate to `ApiExecutor`. `checkResponse` surfaces the backend's `message` and then appends any `error` (string) or `errors` (Laravel validation map, flattened) detail on a new line, so the real cause — not just the generic summary — reaches the user. For a null status (transport failure) it appends GetConnect's `statusText` (e.g. "Broken pipe"). A technical server failure comes back with only a `reference` (no raw `error`) — `checkResponse` appends "Reference: …" so the user can quote it. A `409` with `error_code: expired_batch` throws `ExpiredStockException` instead: the outflow submit (`modules/outflow_order/outflow_submit.dart`, `submitOutflowData`) lists the expired batches/serials and resends with `confirm_expired: true` once the user confirms. `ApiProvider.get` resends a GET **once** when it died on a stale keep-alive socket (`isStaleConnection`: broken pipe / connection reset) — the ngrok tunnel closes idle connections; POST/PUT/DELETE are never resent. **Idempotent submits** — the receive / outflow / work-order-issue POSTs send an `Idempotency-Key` header (`postMap(..., idempotencyKey:)`) from `SubmitKey` (`global/submit_key.dart`), stored in `DraftService` under `<draftScope>:submit_key` so a retry after a lost answer — same screen, reopened screen or app restart — reuses it; the backend's `idempotent` middleware (`EnsureIdempotentSubmit`) replays the saved answer instead of booking the document twice. Wrap the provider call in `SubmitKey(drafts, draftScope).send((key) => ...)` (`submitOutflowData` takes `submitKey:`); the key is dropped on success or on `409 submit_already_saved` (`SubmitAlreadySavedException`). **Stale sessions** — `AuthService.session` is bumped on sign-in/out; `ApiExecutor` drops the error of a call that started under an older session, and a 401 only signs out when the request carried the current token. **Signing out** always goes through `ApiProvider.signOut({notice})`: it revokes the token with `POST /logout` in the background, clears it and returns to login. `checkResponse` calls it for answers that end the session (`ApiProvider.sessionEndNotice`): 401, `403 PASSWORD_CHANGE_REQUIRED` (changed on the web — the app has no change-password screen), `403 TENANT_SUSPENDED`, `402 SUBSCRIPTION_EXPIRED`; a 429 gets "Try again in N seconds" from `retry_after`. The login form validates like the backend (`loginFieldErrors`: username ≥ 3, password ≥ 6) before sending — each attempt counts against the sign-in throttle — and "Forgot Password?" mails a web reset link (`POST /send-email-reset`). Numeric fields the API sends as DECIMAL strings (`"180000000"`) must go through `safeToInt`, never `json[...] ?? 0` into an `int` — except **quantities**, see below.

**Decimal quantities** — order quantities are DECIMAL(18,6) on the backend (kg, metre…), so every qty in the order flows is a `num`, never an `int`: parse with `safeToNum`, sum entries with `sumQty` (rounded to 6 dp, so 0.1 + 0.2 doesn't trip an over-fill guard — wrap other qty arithmetic in `roundQty` before comparing), print with `formatQty` ("2.5", "3" — no "3.0"), and read typed input with `parseQty` (accepts "2,5" or "2.5"). **Serial-tracked UNIQUE/BATCH lines count whole units** (`wholeUnitsOnly(item)`; the backend makes one SKU per unit/batch entry and rejects fractions on both receive and outflow) — pass `wholeUnits:` to the qty dialogs; every other line may be fractional.

**Controller API call pattern** — All API calls go through `ApiExecutor.run()`. After the call, a null check is the only error handling needed:
```dart
final data = await ApiExecutor.run(isLoading: isLoading, task: () => provider.getSomething());
if (data == null) return;   // error already shown by ApiExecutor
// use data directly
```
Never check `response.statusCode`, `response.isOk`, or `response.body?['success']` in a controller.

**Screen chrome (all screens except Home)** — The AppBar is always `appHeader(title, accent:, icon:, subtitle:)`: navy gradient, white back arrow (`Key('appBarBackButton')`, always pops via `closeRoute()`; override with `onBack`), and the module color appears **only** in the white icon tile. Rules: **one accent per page** (the tile's `AppAccent`; icon chips, list cards, pills and progress use it); **buttons are navy** (`navyButton`, the fill/scan bottom bar, the FAB ring) — except a button that opens another module uses that module's color ("Create Delivery" / "View Deliveries" = steel); small accent text on white uses `AppAccent.text` (the `*Dark` shades for sky/amber/sage); API colors go through `readableOnWhite`/`statusPill`. The card under the AppBar is `accentHeaderCard` (no solid gradient block); only the hub hero cards keep a full gradient.

**Order-module UI** — All receive/outflow/delivery screens (menus, lists, selection, details, fill/scan, confirm) are thin compositions over the shared `order_*_widgets.dart` files and the components above; do not hand-roll list cards, header cards, stat cards, or bottom bars. Submit payloads send only `linesToSubmit(items, 'filled' | 'scanned')` (`global/functions.dart`) — the backend saves every line it gets, so an unfilled line became a qty-0 document line + stock transaction (the backend now also skips qty-0 lines and rejects a submit with none). Accents (`AppAccent`): **receive** = `navy` (menu/history) / `sky` (By-PO) / `sage` (By-Supplier); **outflow** = `purple` (menu/history/By-Request) / `amber` (By-Customer) / `sage` (By-Work-Order); **delivery** = `steel`; **inventory** (products, master data, transactions) = `slate`. Hub heroes use `[navyDark, navyMid]`.

**Delivery tracking** — The `delivery` module tracks the logistics leg of a completed outflow order (status Pending/Shipped/Delivered/Cancelled, ETA, address, notes). A delivery is **header-only** (no line items). Created via `POST /outflow-order/createDelivery {id}` — from the outflow detail's "Create Delivery" CTA (shown when `is_have_delivery` is false) **or** the post-submit auto-prompt; both then route to the delivery list (the backend returns no delivery id to deep-link). Status updates go through `PUT /delivery/{id}`, which **requires `status_id` + `estimate_at` + `address` on every call** — quick status buttons resend current values, falling back to the edit form when ETA/address are missing. The app does **not** send `updated_by` — the backend stamps it from the token. Status only moves **forward** (Pending → Shipped/Delivered/Cancelled, Shipped → Delivered/Failed): the detail/update response carries `next_statuses`, and the status panel and edit dropdown offer only those (`DeliveryDetailController.nextStatuses`). The move to **Delivered requires `receiver_name`** (quick button asks via `showReceiverNameDialog`, the edit sheet shows a "Received by" field), and a delivered delivery is **locked** — no edit, no further status. A user with `delivery.undo-status` sees "Undo to `<status>`" (from the detail's `undo` block; `POST /delivery/{id}/undo-status {reason}`). A Delivered delivery shows a **Proof of delivery** card (`delivery_proof_card.dart`): its `proofs[]` plus Take photo / From gallery via `image_picker`, uploaded as multipart `file` to `POST /delivery/{id}/proofs`; tapping a photo proof fetches `GET /delivery/{id}/proofs/{media}/preview` through `ApiProvider.getBytes` (GetConnect decodes every body to a string, so binary files must go through it) and opens `showProofPreview` (pinch to zoom); a non-image proof (a PDF note from the web) says to open it on the web. **Status names vs labels**: `status_name` / `DeliveryStatusModel.name` (Pending, Shipped…) is the stored key — compare against it in logic; what a person reads is the web's label (`status_label`, `DeliveryStatusModel.label`, `undoToLabel`: Pending reads "Scheduled", Shipped "On the way", Failed "Failed / returned") — show only labels. Home's pending count reads `GET /delivery/status-count` (`DeliveryStatusCount`), never the whole `GET /delivery`. Shared create/confirm logic lives in `modules/delivery/delivery_actions.dart`.

**Serial numbers & `manage_sn`** — `manage_sn` (bool on the `items` table, default `false`) is the **single criterion** for serial tracking: **mobile and backend, receive and outflow all gate on it** — never on `serial_number_type` alone. `serial_number_type` (`UNIQUE`/`BATCH`/`OTHER`) only shapes *how* serials are captured when `manage_sn` is on.

- **`manage_sn == true`** — serial-tracked. The backend auto-generates an SKU per unit (UNIQUE) / per batch entry (BATCH) at receive and stores that SKU as **both `serial_number` and `internal_code`**; it is printed on the label. **Workers always scan the printed SKU label** — at receive to *confirm*, at outflow to pick which stock leaves — and a scanned SKU/serial is **required** on every outflow entry.
- **`manage_sn == false`** — quantity-only everywhere. No serials are generated (receive) or attached (outflow), **even for `UNIQUE`/`BATCH`** items; the stock-transaction qty stands on its own.

**Receive fill** (only when `manage_sn`, split by `serial_number_type`): **BATCH** — worker enters a qty per batch via `addFilledSerial`, producing `filled` entries `{serial, qty, expired_date}`; one line can split across several batch entries (5 = 2 + 3), over-fill is guarded and duplicate serials rejected. **UNIQUE / OTHER** — quantity-only via `addFilledQty` `{qty, expired_date}`. Edit/remove by index (`updateFilledAt`/`removeFilledAt`).

**Work-order reservations in By Request** — the request list also returns reservations with **no customer** (work order / material requisition, e.g. `OR-RES-MR-…`). The backend refuses those on a delivery order (INV-D-16), so `OutflowRequestModel.hasCustomer` is false, the card reads "Work order reservation", and the detail is read-only: a notice (`Key('outflowWorkOrderNotice')`), no Fill/Scan, Continue disabled. They are issued from **By Work Order**. A work-order reservation is **never closed** — not when fully issued, not when its work order completes or is cancelled (closing it by hand is refused: "Close the work order instead"; only its Material Requisition's status moves) — so the By Work Order list still shows completed work orders, every line locked by the blocker (owner ruling 2026-11-05: keep them listed).

**By Work Order (issue material to production)** — Outflow → By Work Order lists work orders with open reservations (`GET /outflow-request/work-order-summary`, rows shaped like the customer list so `OrCustomerModel` reads them), then one work order's lines (`GET /outflow-request/{wo}/work-order-summary`, marked by the gates `issueByWorkOrder` runs: work order released/in progress, project/OA not cancelled or completed, approval, cancelled MR, closed reservation). Submit is `POST /outflow-order/issue-by-work-order` (`workOrderIssuePayload`: `or_line_id`, `item_id`, `qty`, scanned serials as `selected_serials`) through the same `submitOutflowData` (409 expired flow) — a JC outflow order with **no delivery prompt**. It **reuses the By Customer views**: `OutflowOrderByWorkOrderController` / `OutflowOrderByWorkOrderDetailController` extend the By Customer controllers and override the hooks (`fetchTargets`/`fetchLines`, `draftScope`, `accent`, `targetLabel`, `startOutflowingItem`); the work-order bindings register them under the By Customer types the views `Get.find`. Change a By Customer view and By Work Order changes with it — read targets/accents from the controller hooks, never hard-code "Customer" or amber there.

**Lines the backend would refuse (read-only)** — the PO/OR line summaries (`/purchase-order/{id}/summary`, `…/supplier-summary`, `/outflow-request/{id}/summary`, `…/customer-summary`) send `can_receive` / `can_issue` + `blocked_reason`, computed by the backend from the same gates the submit runs (`ReceiveOrderService::receiveBlocker` — deleted PO, no price INV-D-06; `OutflowOrderService::issueBlockers` — deleted/closed reservation, no customer, approval, cancelled OA, customer PO number OA-D-21, cancelled MR). The models expose it as `blockedReason` (`lineBlockedReason`), the controllers put it on the line map as `blocked_reason`, and a blocked line is read-only: `orderItemSummaryTile(blockedReason:)` shows a lock + the reason (`Key('orderLineBlockedReason')`) with no Fill/Scan, a stale draft for it is dropped on load, and the fill/scan Continue skips it (`nextOpenLine`). Never re-implement a backend rule in the app to hide a line — add it to the blocker instead. Quantity / free-to-issue stock checks stay at submit (they depend on what is filled).

**Outflow scan** (`_onScanTap`): `manage_sn == false` → quantity-only via `setScannedQty` (`{qty}`); otherwise by `serial_number_type` — **UNIQUE** scans unit-by-unit (`scanUnique`, camera stays open), **BATCH/OTHER** scan once then enter qty (`addScannedCode`). A BATCH label is checked at the scan (`outflow_batch_check.dart`: `batchLeftToScan` reads `GET /item/{id}/serial-number` via `OutflowOrderProvider.getSerialStock`, then `batchQtyFits`; "Edit Code" on a row goes through `canRenameScan` — no duplicate, and a BATCH rename passes the same stock check) — an unknown label or a draw beyond what the batch has left is refused before submit; the backend still enforces both. Serial entries are `{serial_number, qty}` — **the payload key is `serial_number`** (not `code`); non-serial entries are `{qty}`. On the outflow detail `orderItemSummaryTile`, the action reflects this gate: `manage_sn == true` shows **"Scan"** (`qr_code_scanner_rounded`), `manage_sn == false` shows **"Fill"** (`edit_rounded`) — mirroring the receive tiles, since a quantity-only line just fills a qty rather than scanning a label.

**Serial confirmation** — After `createReceiveData` returns the created RO, `startReceivingItem()` routes to the **Confirm Serials** screen (`RECEIVE_ORDER_CONFIRM`). It loads the RO's actual generated serials (`getReceiveOrderSerials`) and shows the labels of `manage_sn` items (the resource sends `manage_sn`; UNIQUE = one label per unit, BATCH = one per batch entry, shown with its qty) — never filter on `serial_number_type`. Finishing with labels still pending asks first; reopened from the Receive Order detail (its FAB shows only when the RO has such labels), Finish pops back to that detail. Scanning a printed SKU label flips it green and POSTs `POST /receive-order/{id}/confirm-serials` (`{codes:[...]}`, one-per-scan or batched), stamping `scanned_at`/`scanned_by` on the `stock_transaction_serials` pivot — persisted and idempotent, so reopening resumes progress. Confirming labels is **not** held by the month close (`closed.period`): a scan changes no qty, price or journal, so labels of a receipt dated in a closed month can still be confirmed — the receipt itself stays locked.

### DRY Code

**Don't Repeat Yourself** — Before adding any widget, helper, or logic, check `global/` for an existing counterpart.

- **Widget reuse**: Shared widgets live in `lib/app/global/widget/`. A widget used in two or more modules must be extracted there, not duplicated.
- **Style reuse**: All text styles come from `AppTextStyle`. Never write `TextStyle(...)` inline if an equivalent `AppTextStyle.*` method exists.
- **Color reuse**: Always use named constants from `variables.dart`. Never copy-paste `Color(0xFF...)` literals.
- **Gradient reuse**: The brand gradient is `[navyDark, navyMid]` (or `[navyDark, navyMid, navyLight]`). Define it once as a local getter — never copy-paste the color list.
- **Data classes**: Use private data classes (e.g. `_MenuConfig`) to configure repeated widget builds instead of copy-pasting widget trees. `_MenuConfig` uses `Color color1, color2` (not hex strings).
- **Section headers**: Repeated heading rows (icon + title) belong in a single `_sectionHeader` helper, not duplicated per-section.
- **Dynamic-height layouts**: Use `Row` + `Expanded` instead of `GridView.extent` when child height should be driven by content. `GridView.extent` forces a fixed aspect ratio and overflows when content exceeds it.
- **No dead code**: Delete commented-out code. Use `git log` to recover it if needed.

### Backend

The Laravel backend lives at **`D:\laravel-project\MasterSystemBackend`**.

The API host comes from the build's env file (`AppConfig`, see **API config** under Commands) — never edit a URL in code. Authentication uses a Bearer token stored by `AuthService` and automatically injected into every request via `httpClient.addRequestModifier`.

**How the app reaches a tenant** — the backend (`stancl/tenancy`, `InitializeTenancyByDomain`) picks the company from the request's **`Host`** header, matched against the central `domains` table; each company has its own database, and a token only works on its own company's host. The central host (`mastersystembackend.test` in dev, `app.<domain>` in production) is not a tenant and serves `workspace/sign-in` / `workspace/forgot-password`.

- **Base URL per request**: `AuthService.apiBaseUrl` (→ `ApiEndpoints.apiBaseUrl`) is direct mode's fixed `API_BASE_URL`, or in workspace mode the signed-in company's `tenantApiHost` (`<scheme>://<api_host>/api`), or the central host while signed out. `ApiProvider` syncs `httpClient.baseUrl` to it before **every** request (`get`/`post`/`put`/`patch`/`delete`/`request`/`getBytes`) — GetConnect joins `baseUrl + path` when it builds a request and always prefixes the base, so never pass an absolute URL to a provider. A provider bound to another host overrides `requestBaseUrl` (and `sendsToken`), as `WorkspaceProvider` does for the central host. A **multipart** body (`FormData`, the proof upload) is encoded before GetConnect joins the URL, so `post`/`put`/`patch`/`request` stamp it with the current `AuthService.session` (`ApiProvider.sessionHeader`, stripped by the request modifier) and the modifier drops it with `SessionChangedException` if the session changed meanwhile — it never reaches the next session's host (`test/helpers/multipart_session_test.dart`). JSON bodies are not stamped: `signOut`'s `POST /logout` must still go out.
- **Email sign-in** (workspace mode): `WorkspaceProvider.signIn` → `handoff` (one company: `tenant.api_host` + a 60 s single-use `handoff_token`) or `choose` (several: `showCompanyChooser`, then sign in again with `tenant_id`). `WorkspaceSession.complete` saves the company **first** (so the base URL is its host), then `POST /sign-in/handoff` → token, `GET /me` → name, roles, `must_change_password` (owed → revoke + `PasswordChangeRequiredException`); any failure clears the half session. `LoginController` runs sign-in + session in **one** `ApiExecutor.run(..., sessionBound: false)` — the sign-in changes the session on purpose, and its errors must still show. The Patrol harness uses the same two classes.
- **Old sessions**: a token stored without a company host is dropped once at `AuthService.init()` in workspace mode (`ApiEndpoints.mustDropStoredSession`); direct mode keeps it.
- **Drafts per company**: `DraftService` stores every scope (and so every `SubmitKey`) as `<tenantId>/<scope>` in workspace mode — PO 42 of one company is not PO 42 of another; direct mode keeps the plain scope.
- **Dev without a tunnel**: `DEV_CONNECT_ADDRESS` makes the request modifier connect to that address and send the real host as `Host` (`ApiEndpoints.connect`), and `NetworkService` probes that address (a `.test` name never resolves on a phone). `ngrok-skip-browser-warning` is only sent to ngrok hosts.
- **`api_host` is the tenant's primary domain** (backend `describe()` → `Tenant::primaryDomain()`, the `domains` row with `is_primary`; one per tenant, kept by `App\Models\Domain`). Tenant `mc` has `mc.mastersystembackend.test` (id 1, primary) and the ngrok domain `allowing-toucan-ghastly.ngrok-free.app` (id 8) — **keep the ngrok row: the Accurate webhook uses it**. To send the app to another host, mark that domain primary (`$domain->makePrimary()`); the row order no longer matters.

When a URL in the env file is stale or wrong, requests return 404/502 or fail to connect. `checkResponse()` in `ApiProvider` catches these and throws `Exception("HTTP 404: Not Found")` (or the server's `message` field if available). `ApiExecutor` surfaces this to the user as a clean snackbar.

**Serial flow (backend)** — `manage_sn` (from the `items` table, surfaced by the PO/OR line `summary` resources) is the single gate: `StockMutationTrait` only touches serials when `manage_sn && serial_number_type ∈ {UNIQUE, BATCH}`.

- **Receive** — `POST /purchase-order/receiveData` → `createReceiveTransactionFromLocal` (`selected_serials => $item['filled']`) generates one `ItemSerialNumber` per unit/batch entry with the **SKU as both `serial_number` and `internal_code`**, plus a `stock_transaction_serials` pivot (`qty` = 1 for UNIQUE, the entry qty for BATCH). `POST /receive-order/{id}/confirm-serials` later stamps `scanned_at`/`scanned_by`.
- **Outflow** — `POST /outflow-request/outflowData` → `createOutflowTransactionFromLocal` attaches exactly the serials the app sent, resolving each via `resolveOutflowSerial()` — matched against `internal_code` **or** `serial_number`, scoped to the line's `item_id` — and marks them out of stock. `OutflowDataRequest` requires `code`/`serial_number` on every scanned entry **when `manage_sn` is true** (`qty` always required). The edit path (`updateOutflowTransactionFromLocal`) mirrors the same `manage_sn` gate, resolving ids via `fillSelectedSerialIds()`.
- **Non-`manage_sn`** lines create only the qty stock transaction — no serials, on either flow. There is **no auto-selection** of serials; they always originate from the app's scan (outflow) or the backend SKU generator (receive).
